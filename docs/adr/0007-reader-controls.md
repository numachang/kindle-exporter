# ADR-0007: リーダー操作子の特定と、表示設定の冪等化

- **ステータス:** 採択
- **日付:** 2026-08-09
- **影響:** [ADR-0005](0005-reader-display-settings.md) の実測 2 と決定 2 を**置き換える**。
  [ADR-0004](0004-page-acquisition.md) 決定 3 のページ遷移方式を具体化する。

## 背景

[ROADMAP](../ROADMAP.md) の残課題「テーマを白にする UI 操作が未特定」を解くため、
設定メニューの DOM を shadow root ごと掘った。目的は達したが、
**ついでに [ADR-0005](0005-reader-display-settings.md) の前提が 1 つ覆った。**

対象: 日本語の縦書き小説（ルビ多数・ページ番号を持たない）、
Kindle Cloud Reader、Chrome 151、viewport 1832x1278。
再現手順は [spikes/settings_menu_dom.py](../../spikes/settings_menu_dom.py) と
[spikes/font_readback.py](../../spikes/font_readback.py)。

## 実測

### 1. テーマの操作子は `#theme-White` などの radio

設定メニュー内に `role="radiogroup"` の `.theme-selector` があり、
その中に 4 つの radio が入っている。

| id | `value` | `aria-label` |
|---|---|---|
| `theme-White` | `White` | 白 |
| `theme-Dark` | `Dark` | 濃い |
| `theme-Sepia` | `Sepia` | セピア |
| `theme-Green` | `Green` | 緑 |

**クリックで切り替わり、`aria-checked` で現在値を観測できる。**
テーマは白・暗の 2 値ではなく 4 値である。

### 2. フォントサイズの現在値は「属性」としてなら読める

[ADR-0005](0005-reader-display-settings.md) 実測 2 は
「`ion-range` の `value` / `min` / `max` は JS から読めない（すべて `undefined`）」
と記録し、そこから決定 2「設定は冪等にできない」を導いていた。

**これは JS プロパティだけを見た結論だった。属性は読める。**

```
ion-range.font-size-slider  getAttribute('value')="5"  min="0"  max="13"
range.value（プロパティ）    null                    ← ADR-0005 が見ていたもの
shadowRoot の .range-tick   14 個（うち .range-tick-active が 6 個）
```

さらに、スライダーの左右に**専用の増減ボタン**がある。

```html
<span role="button" aria-label="フォントサイズを縮小する">A</span>
<span role="button" aria-label="フォントサイズを拡大する">A</span>
```

押すと 1 段ずつ、完全に決定的に動く。

| 操作 | `value` | active tick |
|---|---|---|
| 初期 | 5 | 6/14 |
| 拡大 ×3 | 6 → 7 → 8 | 7 → 8 → 9 |
| 縮小 ×3 | 7 → 6 → 5 | 8 → 7 → 6 |
| 最小まで縮小 | **0** | 1/14 |
| そこから拡大 ×4 | **4** | 5/14 |

**フォントサイズは 0〜13 の 14 段で、現在値が読め、目標値へ確実に到達できる。**
すなわち**設定は冪等にできる。**

### 3. `.click()` は効かない。`Input.dispatchMouseEvent` は効く

ページ送りボタンに対する 2 通りの操作を比較した。

| 操作 | 結果 |
|---|---|
| isolated world から `button.click()` | **動かない** |
| `Input.dispatchMouseEvent`（press + release） | 動く |

一方、設定メニューのトグル（`ion-button`）は `.click()` でも
`Input.dispatchMouseEvent` でも動く。**要素によって効く機構が違う。**
両方に効く `Input.dispatchMouseEvent` に統一すれば、この差を意識せずに済む。

### 4. ページ送りは chevron ボタン。矢印キーは使えない

```
#kr-chevron-left   aria-label="次のページ"   中心 (92, 639)
#kr-chevron-right  aria-label="前のページ"   中心 (1741, 639)
```

**縦書き（右→左に読む）書籍では、左の chevron が「次」である。**

矢印キーは使えない。`Input.dispatchKeyEvent` の ArrowRight は
**フォーカスされている `#kr-scrubber-bar`（位置シークバー）を 1 目盛り動かすだけ**で、
ページ送りにはならなかった。位置が 9783 → 9782 と 1 だけ動いたのがその証拠である
（1 ページは約 41〜55 位置ぶん）。Space キーはページ送りとして機能したが、
「前へ」に対応するキーが無いので採用しない。

**読み進む向きは CSS からは判定できない。** 本文がサーバ側でレンダリングされた
画像である（[ADR-0004](0004-page-acquisition.md)）ため、`#kr-renderer` の
`writing-mode` は `horizontal-tb`、`direction` は `ltr` を返す。
`<html>` の `dir` / `lang` 属性も無い。**向きを知る手段は `aria-label` だけである。**

### 5. 位置表示には「ページ」形式と「位置」形式がある

[ADR-0004](0004-page-acquisition.md) 実測 4 では `33/431ページ` を観測していたが、
本 ADR の対象書籍は**ページ番号を持たず**、`位置9783/10167 ● 96%` と表示する
（`.text-div`）。設定メニューの「本のページ」チェックボックス
（`#page-in-book-item`）は on になっているので、**書籍側にページ番号が無い**。

1 ページあたり 41〜55 位置ぶん進む。

> **後日の実測による訂正:** 「最終ページの位置は総数と一致しないだろう」と
> 推測して決定 6 を書いたが、実際に巻末まで送ったところ
> **`位置10167/10167 ● 100%` と一致した。** 先頭も `位置1/10167` だった。
> 推測を実測として書いてしまっていた。
> なお巻末・先頭の判定には、位置表示より確実な signal がある（実測 11）。

### 6. 所要時間（本設計で最も知りたかった数字）

`kindle_shot` は 8.13 秒/ページだった（[ADR-0001](0001-architecture.md)）。

送り → 確定待ち → 画像取得 のループを 25 ページ × 3 条件で実測した。
確定待ちは「位置表示が変わる、または `<img>` の blob URL が変わって
`complete` になる」で判定し、1 秒待って変化が無ければ再クリックする。

| クリック前の待ち | 中央値 | 平均 | 最大 | クリック回数 |
|---|---|---|---|---|
| **0ms** | **124ms/頁** | 265ms/頁 | 1143ms | 27 / 25 頁 |
| 120ms | 246ms/頁 | 313ms/頁 | 1212ms | 25 / 25 頁 |
| 250ms | 384ms/頁 | 425ms/頁 | 1210ms | 25 / 25 頁 |

**待たずに送り、空振りしたら再クリックするのが最も速い。**
連続クリックは 25 回に 2 回ほど空振りするが、再クリックの費用の方が
一律に待つ費用より安い。

内訳と周辺コスト:

| 項目 | 実測値 |
|---|---|
| ページ画像の取り出し（canvas → PNG dataURL） | **17ms**（2199x1692、約 600KB） |
| 本番ループ 1 ページ（`ke-nav` + `ke-cdp`） | **227ms**（実測 12 で調整後） |
| `Page.getFrameTree` + `Page.createIsolatedWorld` | 1.2ms |
| 既存 isolated world での `Runtime.evaluate` | 0.3ms |
| 観測 1 回（位置・画像・メニュー・テーマをまとめて 1 回で取る） | 0.4ms |

**CDP の呼び出しコストは無視できる。** isolated world を毎回作り直しても
1.2ms なので、性能のために使い回す必要はない。

### 7. 表示設定を変えると、ページ画像が 2.8 秒消える

テーマやフォントサイズを変えると**ページが作り直され、その間 `<img>` が
DOM から消える。** 位置表示も一緒に消える。

`ke-cdp` の実装後に実機で測ったところ、設定変更から再描画完了まで **2.8 秒**だった。

これは設計上の落とし穴である。[ADR-0005](0005-reader-display-settings.md) 決定 2 の
「設定 → 実測」は、**設定直後に測ろうとすると「画像が無い」で必ず落ちる。**
実装当初の `ke-nav` は設定変更から実測まで約 2.1 秒しか置いておらず、
実機では確実に失敗する状態だった。

### 8. ページ送りのクリックには約 100ms の最小間隔がある

これも実装後に見つかった。`ke-cdp` から送ると 1 ページ 1.07 秒かかり、
同じことをする使い捨てスクリプトでは 115ms だった。差の原因を切り分けた結果、
**クリックの間隔**だった。

12 ページを送り、押す前に空ける時間を変えて測った
（押しても反映されなければ 1 秒後に押し直す）。

| クリック前に空ける時間 | 中央値 | 押した回数 / 12 頁 |
|---|---|---|
| 0ms | 1012ms | 19 |
| 50ms | 566ms | 18 |
| **100ms** | **115ms** | **13** |
| 150ms | 174ms | 13 |
| 250ms | 261ms | 14 |

**前の送りから約 100ms 空けないと、クリックは黙って無視される。**
空振りしても DOM には何の痕跡も残らない。

押し直しまでの時間も測った（クリック前は待たない）。

| 押し直しまで | 中央値 | 押した回数 / 12 頁 |
|---|---|---|
| 1000ms | 1027ms | 22 |
| **400ms** | **260ms** | **18** |
| 250ms | 310ms | 23 |
| 150ms | 297ms | 35 |

短くしすぎると空振りを増やすだけで速くならない。**400ms が底**である。

この癖は 2 つの欠陥を生んでいた。

1. **`ke-nav` は空振りを押し直していなかった。** 反映を 8 秒待って諦め、
   「位置」表示の書籍では巻末と誤認する。つまり**本の途中で静かに打ち切る**
2. **巻き戻しの終端判定が 2 回連続の停滞で成立していた。** 空振り 2 回で
   「先頭に着いた」と誤認し、**本の途中から撮り始める**

どちらも出力が黙って壊れる種類の欠陥である。

### 9. 観測を詰めすぎると遅くなる

`Runtime.evaluate` はページのメインスレッドで走る。
間を置かずに観測し続けると描画とイベント処理を圧迫し、かえって遅くなった
（観測間隔 10ms で 1 ページ 1.0 秒、20ms で 297ms）。**20ms 程度が下限**である。

### 10. 遅くなるのは「タブが隠れている」から。Amazon の絞り込みではない

約 200 ページ送ったところで 1 ページ 1.0 秒に落ち、やがてページ画像も
UI ボタンも DOM から消えた。当初これを
**「速く送り続けるとリーダーが応答しなくなる」と記録したが、誤りだった。**

原因は **Chrome のウィンドウが隠れていたこと**である。切り分けた結果:

| 状態 | `visibilityState` | 1 ページ |
|---|---|---|
| ウィンドウが見えている | `visible` | **194〜321ms**（60 ページ連続で劣化なし） |
| ウィンドウを最小化 | `hidden` | 1.0〜1.8 秒 → やがて停止 |
| 最小化を戻す | `visible` | **194ms**（即座に回復） |

最小化 → 停止 → 復元 → 回復、が再現する。**枚数でも時間でもなく、
タブが隠れているかどうかで決まる。**

`Page.setWebLifecycleState`（`active`）と `Emulation.setFocusEmulationEnabled` で
`visibilityState` を `visible` に見せかけることはできたが、**速度は戻らなかった。**
JS から見た状態ではなく、レンダラそのものが絞られている。

効いたのは **Chrome の起動フラグ**である。

```
--disable-backgrounding-occluded-windows
--disable-renderer-backgrounding
--disable-background-timer-throttling
```

これを付けて起動すると、**最小化したままでも 204ms/頁で動く。**
実際に最小化した状態で 36 ページ送り、巻末まで到達できた。

[ADR-0004](0004-page-acquisition.md) の「画面/マウスを占有しない」という利点は、
**このフラグを付けて初めて成立する。**

> **教訓:** 「200 ページ送った後に壊れた」という時系列から
> 「送りすぎが原因」と結論したが、実際には無関係な変数（ウィンドウの状態）が
> 同時に動いていた。ユーザーから「ブラウザ上では動かせる」と指摘されるまで、
> 誤った原因を ADR と ROADMAP の最優先項目に書いていた。

### 11. 巻末・先頭は chevron の**存在**で確定できる

ページ送りボタンの振る舞いには 2 段階ある。

| 状態 | DOM | 矩形 |
|---|---|---|
| その方向へ進める・ポインタがその側にある | ある | 48x48 |
| その方向へ進める・ポインタが反対側にある | **ある** | **0x0** |
| **その方向へ進めない（端にいる）** | **無い** | — |

実測:

- `位置1/10167`（先頭）で DOM にあるのは `次のページ` **だけ**
- `位置10167/10167`（巻末）で DOM にあるのは `前のページ` **だけ**
- 本の途中では両方 DOM にあり、**ポインタのある側だけが 48x48** になる。
  ポインタを右へ動かすと `前のページ` が 48x48、`次のページ` が 0x0 に入れ替わる

したがって:

- **端の判定は「DOM にあるか」で行う。** 「描かれているか」で判定すると、
  ポインタが反対側にあるだけで端だと誤認し、本の途中で撮影を終えてしまう
- **押すときは先にポインタをその側へ動かす。** 隠れている chevron は矩形が
  0 なので座標が取れない。viewport の 5% / 95%・高さ 50% の位置へ
  `mouseMoved` を送ると出てくる（実測値。左右どちらかは分からないので両方試す）

これは位置表示の形式にも、位置表示の有無にも依存しない。
**「送っても進まなくなった」という推測より確実である。**

### 12. 反映を見る間隔が、そのまま次に押すまでの間隔になる

記録・再生ハーネス（ADR-0001 §6b）で実機の 1 冊を記録し、その記録を数えて分かった。

`ke-nav` は「送る → 反映を見る → 撮る → すぐ次を送る」を繰り返すので、
**反映を見る間隔が短いと、次の送りが最小間隔（実測 8 の約 100ms）に足りず空振りする。**
空振りすると押し直しの 400ms が丸ごと乗るため、細かく見るほど逆に遅くなる。

実機で 12 ページずつ、間隔を振って測った。

| 反映を見る間隔 | 送った回数 / 12 枚 | 1 枚 中央値 |
|---|---|---|
| 60ms | 20 | 492ms |
| 120ms | 16 | 288ms |
| **180ms** | **14** | **227ms** |
| 240ms | 14 | 290ms |

**180ms が底。** 60ms から 2.2 倍速い。

この数字は記録から出した。`Observation` の経過時間と `Action` の並びが
残っているので、**実機を止めずに後から数えられる。**
ハーネスを作った利益がそのまま出た形である。

### 13. シークバーの `value` は現在位置を表さない

`#kr-scrubber-bar` は `min="1" max="10167"` を持つが、`value` 属性は
位置 9783 のとき 384、位置 9887 のとき 280 と、**現在位置と無関係な値**を返した。
`aria-label` にだけ現在位置が入る（`aria-label="位置9783"`）。
**巻き戻しの近道には使えない。**

## 決定

### 1. UI 操作はすべて `Input.dispatchMouseEvent` で行う

要素の座標を `getBoundingClientRect()` で取り、その中心に
press + release を送る。`element.click()` は使わない（実測 3）。

### 2. `Action::ClickFontSlider { fraction }` を `Action::SetFontSize { index }` に置き換える

[ADR-0005](0005-reader-display-settings.md) 決定 2 の「スライダー位置を割合で指定し、
毎回最小位置に戻してから目標位置へクリックする」手順は**不要になった。**

- `Observation` は現在のフォント段（`index` と `max`）を持つ
- `Action::SetFontSize { index }` は目標段を直接指定する
- `ke-cdp` は現在段と目標段の差だけ増減ボタンを押す（冪等）

**「設定 → 実測 → 検証」のループ自体は残す。** 段と画素/文字の対応は
書籍と viewport に依存するため、目標は依然「画素/文字」で指定する。
ただし探索は 0〜13 の離散 14 値に対する二分探索になり、**4 回以内に必ず収束する。**

### 3. ページ送りは chevron を `aria-label` で特定する

`#kr-chevron-left` / `#kr-chevron-right` のうち、`aria-label` が
「次のページ」に一致する方を「次」とする。**id や画面上の位置で決めない**
（縦書きと横書きで左右が入れ替わるため。実測 4）。

`aria-label` は表示言語に依存するので、日本語と英語の表記表を持つ。
**どちらにも一致しなければエラーで止める。** 推測して逆向きに撮り続けるより、
止まった方が良い。

### 4. 送りは「最小間隔を空けて押し、届かなければ押し直す」

実測 8 の数字をそのまま定数にする。

| 何を | 値 | 根拠 |
|---|---|---|
| 送りの最小間隔 | 100ms（余裕を見て 120〜150ms） | これより短いと無視される |
| 反映を見る間隔 | 60ms（観測は 20ms より詰めない） | 実測 8・9 |
| 押し直しまで | 400ms | 実測 8 の表で底 |
| 巻き戻しの押下間隔 | 150ms | 毎回押すので間隔を自前で確保する |
| 停滞したあとの間隔 | 800ms | 空振りを停滞と誤認しないため |
| 巻き戻しの停滞しきい値 | 3 回 | 2 回では空振りで誤認する |

**空振りは必ず押し直す。** 押し直さないと、「位置」表示の書籍では
巻末と区別できず本の途中で打ち切ってしまう（実測 8）。

### 5. 表示設定を変えたら、ページが戻るまで待ってから測る

`ke-nav` に「再描画待ち」の状態を置き、ページ画像が使える状態に戻ってから
`MeasurePage` に進む。戻らなければ `PageDidNotRender` で失敗させる（実測 7）。

**模擬（`FakeBrowser` / テスト用のリーダー）にもこの癖を再現させる。**
再現しない模擬でテストしても、実機で落ちる欠陥は見つからない。
実際、実測 7 と 8 を模擬に入れた時点で、それまで通っていたテストのうち
10 件が落ちて欠陥を示した。

### 6. 巻末・先頭は chevron の存在で確定する。位置表示は控えにする

`Observation` に `TurnControls { next, prev }` を持たせ、**chevron が DOM に
あるかどうか**で端を判定する（実測 11）。位置表示の形式にも有無にも依存しない。

- 観測できなければ「端ではない」に倒す。誤って早く終わるより、
  余分に 1 回押して確かめる方が安い
- `PageLabel` の種別（`Page` / `Location`）は残すが、用途は**控え**である。
  chevron が観測できず、かつ送りが止まった場合にだけ使う。
  「位置」形式では巻末と故障を区別できないので `end_confirmed` を `false` にする

### 7. Chrome は絞り込みを無効にして起動する

```
--disable-backgrounding-occluded-windows
--disable-renderer-backgrounding
--disable-background-timer-throttling
```

**これが無いと、ウィンドウを最小化・被覆した時点で capture が実質停止する**
（実測 10）。[ADR-0004](0004-page-acquisition.md) の「画面を占有しない」は
このフラグの上に成り立っている。

### 8. `Theme` は 4 値にする

観測できる現実を型で表せるようにする（`White` / `Dark` / `Sepia` / `Green`）。
OCR に使うのは `White` のままである。

## 影響

- **良い方向:** フォントサイズ設定が冪等になった
  （[ADR-0005](0005-reader-display-settings.md) 決定 2 の「毎回最小位置まで戻す」が消えた）。
  `ke-cdp` 経由の実測で **1 ページ約 300ms**。
  [ADR-0001](0001-architecture.md) の見積り（8.13s/頁 → 0.2〜0.4s/頁）の範囲に入った
- **悪い方向:** ページ送りの向きと設定メニューの開閉が、`aria-label` という
  **表示言語依存の文字列**にぶら下がる。将来必ず壊れる箇所なので、
  一致しなければ推測せず止める設計にした
