# ADR-0004: ページ取得方式（スパイクC の結果）

- **ステータス:** 採択
- **日付:** 2026-08-08
- **影響:** [ADR-0001](0001-architecture.md) の capture / trim フェーズを置き換える。
  [ADR-0003](0003-ruby-and-ocr-accuracy.md) §1「DOM から取れれば OCR 不要」を否定する。

## 背景

[ADR-0003](0003-ruby-and-ocr-accuracy.md) で、「最も精度の高い手法は OCR しないこと」
＝ DOM から実文字を取ることだと結論し、その可否を [ADR-0001](0001-architecture.md) の
スパイク1 に委ねていた。実機で確認した。

対象: 日本語ライトノベル（縦書き・ルビ多数）、Kindle Cloud Reader、Chrome 151。

## 実測

### 1. DOM に本文は存在しない

`DOM.getDocument(pierce=true)` で iframe と shadow root を貫通して DOM 全体を取得した結果:

| 項目 | 値 |
|---|---|
| DOM 全体 | 141,987 文字 |
| うち日本語文字 | **66 文字**（すべて UI。書名・「ページ」・「読書速度を学習中」） |
| `<ruby>` / `<rt>` | **0 件** |
| `<canvas>` | **0 件** |
| `@font-face` | **0 件** |
| 子フレーム | `about:blank` 1 件（`outerHTML` 39 文字＝空） |

画面に表示されている本文（`攻性咒式士`、`アルカーバ` 等）は**どれも DOM 内に存在しない**。
フォント難読化ですらなく、テキストが最初から無い。

**DOM 抽出は不可能。この書籍種別では OCR が必須である。**

### 2. ページはサーバ側でレンダリングされた画像として配信される

本文領域の DOM 構造:

```html
<div id="kr-renderer" class="kg-client-root kg-client-theme--dark">
  <div class="kg-view">
    <div class="kg-full-page-img">
      <img src="blob:https://read.amazon.co.jp/9bc9e05b-..."
           natural="1501x1692" displayed="1001x1128">
```

`<canvas>` でも DOM テキストでもなく、**ページ全体が 1 枚の画像**である。

### 3. そのページ画像を原寸で直接取得できる

`Page.captureScreenshot` は成功する（UI を含めた画面全体が撮れる）。
しかしそれより良い方法がある — **`<img>` の中身を原寸で取り出せる。**

Amazon は `window.fetch` を差し替えているため素の `fetch(blobURL)` は
`TypeError: Failed to fetch` で失敗する。`Page.createIsolatedWorld` で
組み込みが汚染されていない JS 文脈を作り、canvas 経由で取り出す:

```js
const c = document.createElement('canvas');
c.width = img.naturalWidth; c.height = img.naturalHeight;
c.getContext('2d').drawImage(img, 0, 0);
c.toDataURL('image/png');   // blob は same-origin なので canvas は汚染されない
```

スクリーンショットに対する優位性:

| | スクリーンショット | ページ画像の直接取得 |
|---|---|---|
| UI の写り込み | ヘッダー・矢印・進捗バーが入る | **無い（本文のみ）** |
| 解像度 | 表示サイズ 1001x1128 | **原寸 1501x1692** |
| 余白トリミング | 必要 | **不要** |
| 全画面化・ウィンドウ操作 | 必要 | **不要** |
| 画面/マウスの占有 | する | **しない** |

### 4. ページ遷移は DOM から確定検出できる

UI 側の DOM にページ表示が実文字で存在する（`33/431ページ ● 6%`）。
ピクセル差分による推測は不要。

### 5. 解像度はサーバ側で頭打ち

viewport と `deviceScaleFactor` を振って、1 文字あたりの画素数を実測した。

| viewport | dsf | 画像原寸 | 本文行 | 総文字 | 行 CONF | **画素/文字** | ルビ検出 |
|---|---|---|---|---|---|---|---|
| 800x1000 | 1 | 960x1275 | 14 | 393 | **0.926** | 28 | 6 |
| 1100x1300 | 1 | 1320x1725 | 21 | 738 | 0.896 | 29 | 10 |
| 1400x1600 | 1 | 1680x2175 | 28 | 1226 | 0.899 | 29 | 11 |
| 2000x2400 | 1 | 2400x3375 | 43 | 2183 | 0.810 | 30 | 12 |
| 1100x1300 | **2** | 1320x1725 | 21 | 738 | 0.896 | 29 | 10 |
| 1100x1300 | **3** | 1320x1725 | 21 | 738 | 0.896 | 29 | 10 |

読み取れること:

- **画像原寸は常に viewport × 1.2 で、`deviceScaleFactor` は一切効かない**
- **画素/文字は viewport に関係なく 28〜30px で一定。** viewport を広げても
  DPI は上がらず、**リフローで 1 ページの文字が増えるだけ**
- 文字が増えるほど精度は落ちる（CONF 0.926 → 0.810）

つまり **「解像度を上げて精度を稼ぐ」ことはクライアント側からはできない。**
[ADR-0003](0003-ruby-and-ocr-accuracy.md) の合成画像実験で
「解像度を上げても本文精度は変わらない」と結論していたが、
実機ではそもそも**解像度を上げること自体ができない**。

### 6. 実ページでの OCR 品質

viewport 1251x1278（既定）、画像 1501x1692、反転後:

- 本文 25 行、行 CONF 平均 **0.927**（最小 0.683）
- 出力は文章として自然で、固有名詞やルビ付き語も正しく読めている
- ルビ BLOCK 検出は **12 件**。実際のページにはそれより多くのルビがあり、
  **検出漏れがある**
- ルビ認識には系統的な誤りがある — 小書き仮名が大書きになる（`じゅしき` → `ちゆじゆしき`）。
  これは辞書アライメントで機械的に訂正できる種類の誤り

### 7. ページ画像は黒地白字

`kg-client-theme--dark` により、**サーバが暗色テーマでレンダリングした画像**を返す
（CSS の `filter` による反転ではない。`filter: none`）。OCR 前に反転が必要。
リーダーのテーマを明色に切り替えれば白地黒字で取得できる見込みだが、未検証。

## 決定

### 1. capture フェーズは「スクリーンショット」ではなく「ページ画像の取得」にする

[ADR-0001](0001-architecture.md) の `ScreenSource` trait は `PageSource` に改める。
実装は CDP 経由のページ画像取得を第一とする。

```
open ──→ capture ──────────────→ validate ──→ ocr ──→ proofread ──→ assemble
         ページ画像を原寸で取得      白紙・重複     [gpu]   [gpu/llm]     [cpu]
         + 反転
```

### 2. trim フェーズを削除する

取得した画像に UI が写り込まないため、余白トリミングが不要になる。
[ADR-0001](0001-architecture.md) の `trim` フェーズと `min_margins` の概念、
および派生元 `kindle_shot` の `boundary_detector` 相当の実装は**不要**。

反転処理は capture フェーズに含める（1 回の numpy 演算で終わる）。

### 3. ページ遷移は DOM のページ表示で検出する

ピクセル差分による静止待ちを行わない。`Input.dispatchKeyEvent` でページを送り、
DOM のページ番号が変わり、かつ `<img>` の `src`（blob URL）が変わって
`complete` になるのを待つ。これが「確定シグナル」になる。

### 4. viewport は精度と枚数のトレードオフとして設定可能にする

解像度は上げられないので、**1 ページあたりの文字数を減らす**ことが唯一の精度レバーとなる。

- 既定は viewport 1100〜1400 相当（CONF 約 0.90、738〜1226 文字/ページ）
- 精度優先なら viewport を狭める（CONF 0.926、393 文字/ページ、撮影枚数は約 3 倍）
- 書籍単位で設定を上書きできるようにする

リーダー本体のフォントサイズ設定（`Aa` メニュー）が画素/文字を上げられるかは**未検証**。
上げられるなら、それが最も筋の良い精度レバーになる。capture 実装時に確認する。

### 5. ルビの検出漏れを既知の制約として扱う

ルビ BLOCK の検出再現率が不十分である（実ページで 6〜12 件）。
[ADR-0003](0003-ruby-and-ocr-accuracy.md) §2 のアライメント方式は、
**検出されたルビを正しく割り当てる**ことはできるが、
**検出されなかったルビを復元することはできない**。

したがって:

- 本文の形態素解析で「ルビが振られていそうな語」（常用外漢字・難読語）を特定し、
  対応するルビ BLOCK が無い箇所を **「ルビ欠落の疑い」として記録する**
- 校閲フェーズで、その箇所の画像を切り出して再検出・再認識を試みる
- 最終的に埋まらないものは、ルビ無しとして出力し、監査ログに残す

ルビの完全性は保証しない。**保証するのは「出力したルビが正しいこと」と
「取りこぼしを把握できること」**とする。

## 影響

- **良い方向:** capture が大幅に単純化・高速化される（スクリーンショット・全画面化・
  ウィンドウ操作・ピクセル差分・トリミングがすべて消える）。
  画面を占有しないので、実行中も PC を普通に使える
- **悪い方向:** OCR は回避できず、精度の上限がサーバ側の描画解像度（約 29px/文字）で
  決まる。ルビは完全には取り切れない
- [ADR-0001](0001-architecture.md) の crate 構成から `ke-imaging` の余白検出が消え、
  代わりに反転・検証だけの軽い crate になる
- 対象書籍が固定レイアウト（マンガ）の場合も同じ経路で扱える見込み。
  リフロー型でも画像配信だったため、書籍種別による分岐は不要かもしれない（未検証）

## 未検証で残した項目

1. リーダーのフォントサイズ設定で画素/文字を上げられるか（精度レバーとして重要）
2. 明色テーマに切り替えて白地黒字の画像を直接取得できるか
3. マンガ（固定レイアウト）でも同じ `kg-full-page-img` 経路か
4. 洋書・リフロー型の英語書籍では DOM にテキストがあるか
   （あるなら書籍種別による経路分岐の価値が出る）
