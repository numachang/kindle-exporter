# ADR-0005: リーダー表示設定の制御と OCR 精度

- **ステータス:** 採択
- **日付:** 2026-08-08
- **前提:** [ADR-0004](0004-page-acquisition.md) の「未検証で残した項目」1・2 に対する回答

## 背景

[ADR-0004](0004-page-acquisition.md) で、ページ画像の解像度はサーバ側が
viewport × 1.2 で固定しており、`deviceScaleFactor` も効かず、
**画素/文字が約 29px で頭打ち**であることが分かった。
残る精度レバーはリーダー本体のフォントサイズ設定だけだったので、実測した。

## 実測

### 1. 表示設定は localStorage 経由では変更できない

設定は `localStorage["KWR_Display_Settings"]` に入っている。

```json
{"theme":1,"fontId":"TBMincho","fontSizeIndex":5,"fontSize":19.8,
 "sideMarginsSize":"narrow","maxNumberColumns":2,
 "fontByWritingSystem":{"Japanese":"TBMincho", ...},
 "preferredThemes":{"Dark":"Dark","Light":"White"}}
```

`fontSizeIndex` を 5 / 8 / 11 / 14、`maxNumberColumns` を 1 / 2 に書き換えて
リロードする組み合わせを 5 通り試したが、**5 通りすべてが完全に同一の結果**だった
（画像原寸 2197x1692、43 行、1438 文字、画素/文字 29、CONF 0.922）。

**リーダーは localStorage を描画設定の入力として使っていない。**
書き込んでもリロード時にリーダー自身が上書きする（`fontId` が
`Bookerly` → `TBMincho` に書き換わることからも、書き込み方向のみのミラーだと分かる）。

### 2. UI の ion-range をクリックすれば制御できる

「リーダー設定」（`aria-label="リーダー設定"`）を押すと `ion-menu` が開き
（判定は `classList.contains('show-menu')`。`ion-backdrop` は出ない）、
フォントサイズは `<ion-range>` のスライダーとして現れる。

`Input.dispatchMouseEvent` でスライダー上の座標をクリックすると設定が変わる。
**capture フェーズは書籍ごとに最適なフォントサイズを自動設定できる。**

なお `ion-range` の `value` / `min` / `max` は JS プロパティとして読めない
（すべて `undefined`）。**現在値を読み取れないため、位置を割合で指定して
結果を実測で確認する方式にする必要がある。**

### 3. フォントサイズは最大の精度レバー

viewport 1831x1278、明色テーマ、同一ページで測定。

| スライダー位置 | 画素/文字 | **ルビ列の幅** | 文字/ページ | 行数 | 行 CONF | ルビ検出数 |
|---|---|---|---|---|---|---|
| 5% | 27 | 11px | 1796 | 43 | 0.883 | 20 |
| 35% | 27 | 11px | 1796 | 43 | 0.883 | 20 |
| **65%** | **45** | **20px** | 536 | 22 | **0.929** | 8 |
| **95%** | **51** | **22px** | 441 | 19 | **0.930** | 9 |

- 画素/文字は **27 → 51 で 1.9 倍**
- ルビ列の幅は **11px → 22px で 2 倍**
- 行 CONF は 0.883 → 0.930
- 代償は 1 ページあたりの文字数が **1796 → 441 で約 4 分の 1**（撮影枚数が約 4 倍）

5% と 35% が同値なのは、スライダーが離散段階を持つためと思われる。

### 4. ルビ認識はフォントサイズで実用域に入る

PARSeq は入力を高さ 24px に正規化するため、**ルビ列の幅が 24px に近いほど有利**である。

同一ページのルビ列を一括認識した結果:

| | 小フォント（ルビ 11px） | 大フォント（ルビ 22px） |
|---|---|---|
| ルビ conf | 0.28 〜 0.69 | **0.63 〜 0.84** |
| 出力例 | `ましようけんいすいすい`<br>`エヒとうけん 七〇`<br>`ベツドベンチ`<br>`のがえぐ` | `かぐられき`（神楽暦）<br>`まぶ`（眩）<br>`ベンチ` / `つか` / `こうおう`<br>`ちゆじゆしき`（咒式） |

破綻した出力が消え、読める形になった。

### 5. 残る誤りは「小書き仮名が大書きになる」系統的な偏り

大フォントでも `じゅしき` が `ちゆじゆしき` になる。
`ゅ` → `ゆ`、`ゃ` → `や`、`ょ` → `よ`、`っ` → `つ` という一方向の誤りである。

**これはランダムな誤認識ではない。** NDLOCR は国立国会図書館のデジタル化資料
（近代の印刷物）で学習されており、その時代の日本語表記は**拗音・促音を
大書きの仮名で書く**のが通例である。モデルはその表記に引かれていると考えられる。

系統的な偏りであることは、後段にとって好材料である。[ADR-0003](0003-ruby-and-ocr-accuracy.md) §2 の
辞書アライメントで、**照合前に小書き／大書きを正規化すれば機械的に吸収できる。**

### 6. 明色テーマにすると白地黒字で取得できる

リーダーのテーマを白にすると、ページ画像自体が白地黒字で配信される
（輝度 mean 238.8）。[ADR-0004](0004-page-acquisition.md) で必要としていた
**反転処理が不要になる。**

## 決定

### 1. capture フェーズは起動時にリーダーの表示設定を UI 操作で確定させる

`open` フェーズの一部として、以下を UI 操作で設定する。

1. テーマを白にする（白地黒字で取得し、反転処理を省く）
2. フォントサイズを目標値に合わせる
3. 設定メニューを閉じる

localStorage 経由は無効なので、`aria-label="リーダー設定"` のボタンを押し、
`ion-menu` に `show-menu` が付くのを待ち、`ion-range` の座標をクリックする。

### 2. フォントサイズは「スライダー位置の割合」で指定し、実測で確定する

`ion-range` の現在値を読み取れないため、**設定は冪等にできない。**
そこで capture フェーズは次の手順を取る。

1. スライダーを最小位置（0%）までクリックして既知の状態にする
2. 目標位置までクリックする
3. **1 ページ取得して画素/文字を実測し**、目標範囲に入っているか確認する
4. 外れていれば位置を調整して再試行する

この「設定 → 実測 → 検証」のループは、[ADR-0001](0001-architecture.md) の
純粋状態機械で表現でき、fake で全分岐をテストできる。

### 3. 既定はスライダー 65% 相当（画素/文字 45、ルビ 20px）とする

95% との差はごくわずか（CONF 0.929 / 0.930、ルビ 20px / 22px）である一方、
1 ページあたりの文字数は 536 と 441 で **65% の方が撮影枚数が 2 割少ない。**

- **既定:** 画素/文字 45 前後を目標にする
- **ルビ優先:** 画素/文字 50 前後（ルビの多い書籍・難読語の多い書籍）
- **速度優先:** 画素/文字 30 前後（ルビが無い実用書など。撮影枚数が 4 分の 1）

書籍ごとに `manifest.json` で上書きできるようにする。

### 4. 小書き仮名の正規化を辞書アライメントの前処理に入れる

ルビ文字列と辞書の読みを照合する前に、双方を「大書き仮名」へ正規化する
（`ゃゅょっぁぃぅぇぉ` → `やゆよつあいうえお`）。
照合が成立したら、**辞書側の表記を採用する**（辞書は正しい小書きを持っている）。

これにより §5 の系統誤差は完全に吸収される。

## 影響

- `open` フェーズに「表示設定の確定」ステップが加わる。
  設定できたかを実測で検証するため、1 ページ分の余分な取得が発生する（1 冊につき 1 回）
- **反転処理が不要になる**（[ADR-0004](0004-page-acquisition.md) の決定 1 から削除）
- 撮影枚数が既定設定で約 3.4 倍に増える（1796 → 536 文字/ページ）。
  capture はページ画像を取るだけで軽いが、**capture フェーズが全体の律速になる**見込み。
  [ADR-0001](0001-architecture.md) の所要時間見積りは capture 側を測り直す必要がある
- OCR 側の総処理量は文字数で決まるためほぼ変わらない。
  ページ数に比例するレイアウト検出（GPU 24ms/ページ）だけが増えるが、無視できる

## 未検証で残した項目

1. `sideMarginsSize` と `maxNumberColumns` を UI から変えたときの効果
   （余白を狭く・1 段組にすれば、同じフォントサイズでより多くの文字が入る可能性）
2. 全画面表示（`aria-label="全画面表示"`）にしたときの画像サイズ
3. capture 実測値。既定設定での 1 ページあたり所要時間と、1 冊あたりの総枚数
