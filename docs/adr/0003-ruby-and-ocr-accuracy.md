# ADR-0003: ルビの扱いと OCR 精度戦略

- **ステータス:** 採択（スパイクC の結果により §2 の適用範囲が変わる）
- **日付:** 2026-08-08

## 背景

[ADR-0001](0001-architecture.md) の後に、2 つの要件が追加された。

1. **日本語にはルビがあるため、ルビも高精度にテキスト化すること**
2. **OCR は必ず精度に揺れが出る。** ①そもそも高精度に読み取れる手法を採る
   ②読み取ったものをローカル LLM 等で校閲できるようにする

これらは後付けの機能ではなくアーキテクチャに影響するため、実測してから設計を決めた。

## 実測（2026-08-08）

測定環境: Ryzen 7 9700X (8C16T) / RTX 4070 Ti 12GB / CUDA Toolkit 13.0 /
onnxruntime-gpu 1.28.0 / NDLOCR-Lite (2026-08 時点の master)

### 実験1: ルビ付き縦書きページに対する NDLOCR-Lite の挙動

Chrome で `writing-mode: vertical-rl` + `<ruby><rt>` の HTML をレンダリングし、
正解が既知のテスト画像を 1x / 2x / 3x の解像度で生成して NDLOCR-Lite にかけた。

**結果1: 本文は完全に正確だった。**

```
吾輩は猫である。名前はまだ無い。どこで生れたか頓と見当がつかぬ。
何でも薄暗いじめじめした所でニャーニャー泣いていた事だけは記憶している。
```

1x（900x1200、本文 22px）で誤り 0 文字。3x でも出力は完全一致で、
**解像度を上げても本文精度は変わらなかった**（1x で既に上限に達している）。

これは入力が**スキャン画像ではなく、ブラウザが描画した born-digital のテキスト**
だからである。NDL の想定用途（劣化した紙面のデジタル化）より条件がはるかに良い。

**結果2: ルビは検出されるが、認識されない。**

```xml
<LINE TYPE="本文" ... STRING="吾輩は猫である。名前はまだ無い。…" />
<BLOCK TYPE="ルビ" X="818" Y="81" WIDTH="11" HEIGHT="598" CONF="0.787" />
<BLOCK TYPE="ルビ" X="772" Y="82" WIDTH="11" HEIGHT="686" CONF="0.832" />
```

レイアウトモデル (DEIM) にはルビ専用クラス `block_rubi` があり、ルビ列を
confidence 0.74〜0.84 で正しく検出する。しかし `src/ocr.py` は
`root.findall(".//LINE")` で LINE 要素だけを認識器に渡すため、
**BLOCK として出力されるルビは文字認識に回らず、STRING を持たない。**

重要なのは、**ルビが本文に混入していない**ことである。本文行は純粋な本文だけを含む。
つまり「ルビが本文を汚す」最悪のケースではなく、「ルビが bbox 付きで分離されている」
という、後から拾うのに最も都合の良い状態にある。

**結果3: ルビ列を切り出して PARSeq に通すと、列単位の一括認識で 96% 読めた。**

| 列 | 正解（連結） | 一括認識の結果 | 文字精度 |
|---|---|---|---|
| 0 | わがはいねこなまえなうとんけんとう | わがはいねこなまえなうとんけんとう | 34/34 |
| 1 | なんうすぐらところにゃーにゃーなこときおく | なんうすぐらところにゃーに**ャ**ーなこときおく | 20/21 |
| 2 | わがはいはじにんげんみきしょせいにんげんちゅういちばんどうあく | わ**か**はいはじにんげんみ**さ**しょせいにんげんちゅうい**も**ばんどうあく | 28/31 |
| 3 | しゅぞく | しゅぞく | 4/4 |
| 4 | しょせいときどきわれわれつかまにくはなし | しょせいときどきわれわれつかまにくはなし | 20/20 |

合計 **106/110 ≈ 96%**。

一方、**空白でルビ群に分割してから個別認識すると精度が激しく劣化した**
（`11` `六八` `3.` などの明らかな誤り）。PARSeq は行単位の認識器であり、
1〜2 文字の断片を与えると文脈を失って壊れる。**列単位で一括認識するのが正しい。**

解像度を 3x にしても改善しなかった。PARSeq は入力を 24x768 に強制リサイズするため、
元画像を大きくしても最終的に同じ解像度に潰される。**解像度を上げる戦略は無効。**

### 実験2: GPU（CUDA EP）の効果

| モデル | 役割 | CPU | CUDA | 比 |
|---|---|---|---|---|
| DEIM (deim-s-1024x1024) | レイアウト検出（1 ページ 1 回） | 235.6 ms | **23.9 ms** | **9.9x** |
| PARSeq (24x768) | 文字列認識（1 ページ 15〜40 行） | 33.2 ms | 46.1 ms | **0.7x（GPU が遅い）** |

PARSeq が GPU で遅いのは、モデルが小さくバッチ 1 固定のため、
カーネル起動のオーバーヘッドが計算時間を上回るからである。

**バッチ化は現状できない。** 配布 ONNX は入力が `[1, 3, 24, 768]` で固定されており、
入力の次元名を `N` に書き換えても、グラフ内部の Reshape ノードにバッチ 1 が
ハードコードされているため失敗する。

```
Reshape node '/encoder/blocks/blocks.0/attn/Reshape':
  Input shape:{8,576,576}, requested shape:{1,576,3,3,64}
```

バッチ化には PyTorch チェックポイントからの再エクスポートが必要だが、
重みはリポジトリに含まれていない。DEIM もバッチ 2 以上で
デコーダの GatherElements が失敗する。

CPU 側のスレッド並列は有効で、セッションを複製して並列実行すると:

| 並列数 | スループット |
|---|---|
| 1 | 13.3 行/秒 |
| 4 | 34.0 行/秒 |
| **8** | **39.3 行/秒（最良）** |
| 16 | 34.3 行/秒（頭打ち） |

なお `onnxruntime-gpu` は CUDA 12 系の pip パッケージ（`nvidia-cudnn-cu12` 等）が
無いと `cudnn64_9.dll` のロードに失敗して CUDA EP が使えない。
セットアップ手順に含める必要がある。

## 決定

### 1. 「そもそも高精度に読み取る」の第一手は OCR しないこと

本文が born-digital である以上、**最も精度の高い手法は DOM から実文字を取ることである。**
[ADR-0001](0001-architecture.md) の未解決スパイク1 を、単なる「撮影可否」から
**「DOM に本文とルビが構造として存在するか」**の確認に拡張する。

DOM にテキストがある場合、リフロー型書籍については:

- 本文精度は 100%（元データそのもの）
- ルビは `<ruby><rt>` から**構造ごと**取得でき、位置合わせの問題が発生しない
- OCR フェーズ自体が不要になり、校閲フェーズも不要になる

OCR 経路は**固定レイアウト書籍（マンガ・一部の教科書）専用**に縮退する。

この結果が出るまで、以下の 2〜4 は「OCR 経路にのみ適用される設計」として扱う。

### 2. ルビは「列単位で一括認識し、本文と突き合わせて整合させる」

OCR 経路でのルビ復元は次の手順とする。

1. DEIM が出す `BLOCK TYPE="ルビ"` の bbox を採用する（NDLOCR-Lite 本体は捨てている）
2. **ルビ列を分割せず、列全体を 1 本の文字列として PARSeq に通す**（実測 96%）
3. 同時に、列内の空白位置からルビ群の Y 範囲を取り出す（**位置情報としてのみ使う**）
4. 本文行（精度 100%）を形態素解析して各漢字列の読み候補を得る
5. 読み候補列と、OCR したルビ文字列を **DP でアライメント**し、ルビ群ごとに割り当てる

この設計の要点は、**本文とルビが互いを検証すること**である。

- 本文は信頼できるので、辞書から得た読みが**ルビ OCR の誤りを訂正する**
  （`わかはい` → 吾輩 の読みは `わがはい`）
- ルビは**辞書の読み曖昧性を解消する**（`一番` の `いちばん` / `ひとばん` など）
- 3 の Y 範囲は、どのルビ群がどの漢字に付くかの**位置的な制約**として効く

アライメントが破綻した箇所（読み候補と一致しない、群数が合わない）は
**捨てずに「未確定ルビ」として記録し**、校閲フェーズに送る。

### 3. 信頼度スコアを誤り検出に使わない

NDLOCR-Lite が同梱するサンプル出力を確認したところ、明らかな誤認識
（`気送子` → `気送手`、`気送子送付管` → `受送子送子管`）に対して
CONF は 0.93〜0.95 と高いままだった。

**したがって「低信頼度の箇所だけ校閲する」設計は成立しない。**
校閲フェーズは信頼度で対象を絞らず、全文を対象とする。
信頼度は補助的な優先度付けにのみ使う。

### 4. 校閲は独立フェーズとし、LLM に自由な書き換えをさせない

ワークフローに `proofread` フェーズを追加する。

```
… → ocr → proofread → assemble
           [gpu/llm]
```

- **独立フェーズにする理由:** 何度でも再実行でき、モデルを差し替えて比較でき、
  校閲なしの出力とも比較できる。[ADR-0001](0001-architecture.md) のフェーズ設計に自然に乗る
- **LLM に自由記述をさせない。** 出力は本文ではなく**編集操作のリスト**
  （位置・変更前・変更後・理由・確信度）とする。本文をまるごと書き直させると
  ハルシネーションが混入し、しかも検出できない
- **各編集を機械的に検証する。** 変更前後の編集距離が閾値を超えるもの、
  ページ画像の該当箇所と矛盾するものは自動的に棄却する
- **監査証跡を残す。** `text/<page>.corrections.json` に全編集を記録し、
  `--review` で差分を確認できるようにする。校閲済みテキストと原文の両方を保持する
- ルビについては、②で「未確定」となった箇所を優先的に提示する

モデルは差し替え可能にする（RTX 4070 Ti の 12GB VRAM に収まる日本語対応モデルを想定）。
どのモデルを既定にするかは、校閲フェーズを実装する時点でベンチマークして決める。

### 5. OCR 経路の実行構成

実測に基づき、**検出は GPU、認識は CPU 8 並列**とする。

| 工程 | 実行先 | 実測 |
|---|---|---|
| DEIM レイアウト検出 | **GPU** | 23.9 ms/ページ |
| PARSeq 文字列認識 | **CPU 8 並列** | 25.4 ms/行 |

1 ページ 20 行と仮定すると **約 0.53 秒/ページ**。12,221 ページで **約 1.8 時間**。
検出（GPU）と認識（CPU）は別資源なので、ページをずらしてパイプライン化できる。

「GPU があるから Windows で画像処理」という当初の想定は、実測により
**「レイアウト検出だけが GPU で 10 倍速く、文字認識は CPU の方が速い」**に修正される。
[ADR-0001](0001-architecture.md) の「GPU が効くのは OCR 推論だけ」という整理は
さらに絞り込まれ、**GPU が効くのは OCR のうち検出だけ**となる。

PARSeq のバッチ化は将来の最適化候補として残す（PyTorch 重みが入手できれば
再エクスポートで GPU バッチ推論が可能になり、認識時間を大幅に短縮できる見込み）。

## 影響

- ワークフローに `proofread` フェーズが増える
- OCR 経路のデータモデルに「ルビ」と「未確定ルビ」が加わる。
  `text/<page>.json` は本文行・ルビ列・アライメント結果・信頼度を保持する必要がある
- 形態素解析器（読み付き）への依存が増える。OCR 経路にのみ必要
- セットアップに CUDA 12 系ランタイムの pip パッケージが必要になる
- スパイクC の結果次第で、2〜5 の適用範囲がマンガ・固定レイアウト本に限定される

## 実験の再現手順

スパイクのスクリプトは本リポジトリには含めていない（使い捨てのため）。
再現する場合は以下を行う。

1. Chrome で `writing-mode: vertical-rl` + `<ruby><rt>` の HTML を
   `--headless --screenshot --force-device-scale-factor=N` でレンダリング
2. `python src/ocr.py --sourceimg <png> --output <dir>` で XML を得る
3. XML の `BLOCK TYPE="ルビ"` の bbox で元画像を切り出し、
   `src/parseq.py` の `PARSEQ.read()` に列全体を渡す
4. GPU は `onnxruntime-gpu` + `nvidia-cudnn-cu12` + `nvidia-cublas-cu12` +
   `nvidia-cuda-runtime-cu12` を入れ、`nvidia/*/bin` を
   `os.add_dll_directory()` に追加してから `InferenceSession` を作る
